**Input**: User description: "Generate proper-size thumbnails for images shared in chat — for the chat bubble, the album/grid view, and the slider thumbnails at the bottom of the viewer (3 sizes). Make them easy to clean up in storage-management settings and per-chat. In the meantime, review the image album view and make sure it's robust and fluid with easy navigation."

## Overview

Ring's chat images have **no persisted, purpose-fit thumbnails today**: the chat bubble renders the
**full image** scaled down by CSS (so scrolling a media-heavy chat decodes full-resolution images),
the all-media grid generates a 400px thumbnail **on-demand and never saves it** (re-encoding it on
every visit), and the full-screen viewer's bottom slider reuses that 400px thumbnail for ~44px
cells. This wastes decode time, memory, and storage, and makes media-heavy chats janky.

This feature does two coupled things:

1. **Three-tier image thumbnails, generated by the sender and sent E2EE.** Every shared image
   carries three purpose-fit thumbnails — **bubble**, **grid**, and **strip** — alongside the full
   image. The sender generates them and transmits them inside the **same sealed end-to-end-encrypted
   envelope** that already carries the video poster, so a recipient sees a preview in the bubble and
   grid **before (or without) downloading the full image** (Ring supports deferred/disabled
   auto-download). Each surface uses its own tier; the full image loads only for the viewer's main
   image. Thumbnails are persisted per message locally, so nothing is re-encoded on revisit.

2. **An album-view robustness + fluidity overhaul.** The full-screen viewer, the all-media grid, and
   the in-bubble album grid are hardened (no out-of-bounds/empty-album breakage, placeholders for
   cleared/undownloaded items, bounded memory) and made fluid and easy to navigate (index counter,
   keyboard navigation, reliable strip centering, smoother zoom↔swipe, restored scroll position),
   accessible (alt text, focus management), and correct in RTL and light/dark.

Plus **thumbnail-aware cleanup**: storage accounting and deletion account for every tier, deletion
removes all variants, there's a "free space but keep previews" option, and cleanup is reachable both
**globally** (Storage management) and **per-chat**.

**Zero-knowledge**: thumbnails are encrypted on the client and ride the existing sealed envelope; the
server still only relays opaque ciphertext (a slightly larger blob). This crosses the client/server
boundary, so a **zero-knowledge checklist is REQUIRED** (Principle I).

Builds on the existing media pipeline (media-encode / media-meta / media-jobs / media-transfer / the
`Media` store) and the spec-1011/1012/1013 chat work.

## Clarifications

### Session 2026-06-19

- Q: Album-view findings — separate spec or folded in? → A: **Folded into this spec** (one combined
  feature: 3-tier thumbnails + album-view robustness/fluidity overhaul).
- Q: How are image thumbnails produced — sent by the sender or generated per device? → A: **Sender
  generates and sends them E2EE** (in the existing sealed envelope, like the video poster), so the
  recipient previews before/without downloading the full image. (Requires the zero-knowledge checklist.)
- Q: Thumbnail tier max-edge sizes? → A: **strip 128px, grid 320px, bubble 512px** (sharp on retina
  at the ~44px / ~130px / ~240px display sizes; small payload).
- Q: "Keep thumbnails, delete originals" then opening the image full-screen? → A: **Re-download the
  original on demand** (it remains on the server as sealed ciphertext until expiry/cleanup), showing
  the largest kept thumbnail upscaled as a placeholder while it fetches; if the original is
  unavailable (offline / purged), stay on the upscaled thumbnail with a retry/download affordance.
- Q: Do videos also get the new tiers? → A: **Yes — grid + strip tiers, downscaled from the video's
  existing poster image (no video re-encode)**; the video bubble keeps using the poster. So the grid
  and strip render small, right-sized thumbnails for both images and videos.
- Q: Backfill existing on-device media, or forward-only? → A: **Backfill** — a one-time, bounded
  background pass generates the tiers for media already on the device; not-yet-downloaded legacy media
  gets its tiers when it's fetched.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Fast image previews everywhere, before download (Priority: P1) 🎯 MVP

A shared image shows a crisp preview instantly in the chat bubble, in the all-media grid, and in the
viewer's bottom strip — each at an appropriate size — and the recipient sees the bubble/grid preview
even before the full image is downloaded. Scrolling a media-heavy chat stays smooth.

**Why this priority**: This is the headline ask and the biggest user-felt win (instant, smooth
previews; previews before download). Everything else builds on the tiers existing.

**Independent Test**: Send an image from A to B with B's auto-download off. On B, the bubble and the
all-media grid show a preview without downloading the full image. Scroll a chat with many images and
confirm it stays smooth (no full-resolution decode per bubble). Reopen the all-media grid and confirm
previews appear instantly (no re-encode/loading flash).

**Acceptance Scenarios**:

1. **Given** an incoming image and auto-download off, **When** the chat (and the all-media grid) is
   viewed, **Then** a bubble/grid preview is shown without the full image being downloaded.
2. **Given** a chat with many images, **When** the user scrolls it, **Then** the bubbles render from
   the small bubble thumbnail (no full-resolution image decoded per bubble).
3. **Given** the all-media grid was opened once, **When** it is reopened, **Then** thumbnails appear
   immediately from storage (no regeneration/loading flash).
4. **Given** the full-screen viewer, **When** the bottom strip is shown, **Then** the strip renders
   from the smallest (strip) tier, and the main image uses the full image.

---

### User Story 2 - The album view is robust (never breaks) (Priority: P1)

The full-screen viewer and grids behave correctly in every edge case: empty albums, an item deleted
or cleared while open, items that aren't downloaded yet, very large albums, and mixed image/video —
no broken images, no out-of-range crashes, no runaway memory.

**Why this priority**: These are real defects (out-of-bounds index on deletion, broken `<img>` for
cleared media, unbounded full-res memory) that can break or crash the viewer; correctness gates a
good experience.

**Independent Test**: Open the viewer, then delete/clear the media it's showing → the viewer recovers
(placeholder or graceful close), never a broken image or crash. Swipe a large album and confirm
memory stays bounded (off-screen full images are released).

**Acceptance Scenarios**:

1. **Given** the viewer is open on an item, **When** that item (or all media) is deleted/cleared,
   **Then** the viewer shows a placeholder or closes gracefully — never a broken image or an
   out-of-range error.
2. **Given** an item that isn't downloaded yet or was cleared to free space, **When** it appears in
   the viewer, **Then** a clear placeholder is shown (not a broken image).
3. **Given** a large album, **When** the user swipes through many items, **Then** memory stays
   bounded (off-screen full-resolution images are released).
4. **Given** rapid swiping, **When** the user lands on a new item, **Then** it is shown at fit (zoom
   does not bleed across items) and the correct item is active.

---

### User Story 3 - Easy, fluid navigation (Priority: P2)

Navigating an album feels WhatsApp/Telegram-grade: you always know where you are, can move by
keyboard as well as swipe, the bottom strip tracks the active item, zoom and swipe don't fight, and
closing returns you to where you were.

**Why this priority**: Fluidity and orientation make the viewer pleasant; valuable but layered on the
working/robust base (US1/US2).

**Independent Test**: Open a 40-image album; confirm a position indicator ("3 / 42"); navigate with
arrow keys and close with Escape; the bottom strip centers the active item; closing returns to the
same scroll position in the grid/chat.

**Acceptance Scenarios**:

1. **Given** the viewer is open, **When** any item is shown, **Then** a position indicator shows the
   current item and total.
2. **Given** a keyboard, **When** the user presses left/right or Escape, **Then** the viewer moves
   between items or closes, with focus managed (trapped while open, restored on close).
3. **Given** the user swipes between items, **When** an item becomes active, **Then** the bottom
   strip scrolls to keep it centered/visible.
4. **Given** the user opened the viewer from the grid (or a chat bubble), **When** they close it,
   **Then** they return to the same scroll position they left.

---

### User Story 4 - Clean up image storage easily (Priority: P2)

The user can see and reclaim storage used by images **and** their thumbnails, both app-wide and for a
single chat, including freeing the large originals while keeping the small previews.

**Why this priority**: Storage control is the second explicit ask; depends on the tiers existing
(US1) so it can account for and purge them.

**Independent Test**: In Storage management, the per-type and per-chat totals include thumbnail bytes;
deleting a chat's images removes their thumbnails too; a "keep thumbnails, delete originals" action
frees most space while previews still render. The per-chat media screen defaults to cleaning that
chat.

**Acceptance Scenarios**:

1. **Given** stored images with thumbnails, **When** the user views storage usage, **Then** the
   totals (by type and by chat) include the thumbnail bytes, shown distinctly from originals.
2. **Given** a cleanup action that deletes media, **When** it runs, **Then** all of that media's
   thumbnail tiers are removed too (no orphans).
3. **Given** the "free space but keep previews" action, **When** it runs, **Then** full images are
   removed but the bubble/grid/strip previews still render.
4. **Given** the per-chat all-media screen, **When** the user cleans up, **Then** it defaults to THIS
   chat, with an explicit app-wide option.

---

### User Story 5 - Accessible, RTL- and theme-correct viewer (Priority: P2)

The album view works for everyone: screen-reader labels on images and controls, keyboard reachability
(US3), correct swipe direction and layout in RTL, and a viewer that respects light/dark rather than
always-black.

**Why this priority**: Constitution X/XI obligations; currently the viewer has empty alt text, is
hardcoded black, and navigates with a physical scroll property that inverts in RTL.

**Independent Test**: With a screen reader, images/controls are announced meaningfully. In RTL,
swiping and the strip order are correct. In light mode, the viewer is not forced black; contrast is
adequate.

**Acceptance Scenarios**:

1. **Given** assistive tech, **When** the viewer or grid is used, **Then** images and controls have
   meaningful labels (not empty), and the viewer is operable without a pointer.
2. **Given** an RTL locale, **When** the user swipes the album, **Then** navigation direction and the
   strip order are correct (no inversion).
3. **Given** light mode, **When** the viewer opens, **Then** it uses the app's theme (not a hardcoded
   black background) with adequate contrast.

### Edge Cases

- **Keep-thumbnails-then-open**: full image deleted but thumbnails kept — opening the viewer's main
  image **re-downloads the original on demand** (still on the server as sealed ciphertext until
  expiry/cleanup), showing the largest kept thumbnail upscaled while it fetches; if the original is
  unavailable (offline / purged server-side), it stays on the upscaled thumbnail with a
  retry/download affordance.
- **Sender on a slow/expensive link**: generating + sending three extra thumbnails adds upload bytes;
  generation must not block the send pipeline (background, like existing media jobs).
- **Very large / odd-aspect images** (panoramas, 1px-tall): thumbnail generation must cap dimensions
  sensibly and not produce degenerate sizes.
- **Legacy messages** (sent before this feature) have no tiers: surfaces fall back gracefully (full
  image or the legacy poster) and may generate tiers locally on demand.
- **Animated images / non-photo formats**: thumbnails are still images of the first frame/content.
- **Group messages**: thumbnails travel per the existing per-recipient media path.
- **Empty album / single item / all-cleared-while-open**: covered by US2.

## Requirements *(mandatory)*

### Functional Requirements

**Three-tier thumbnails (US1)**

- **FR-001**: For each shared image, the sender MUST generate three thumbnail tiers in addition to the
  full image, at max-edge sizes **strip 128px, grid 320px, bubble 512px**, each encoded at a quality
  tuned for small size with acceptable sharpness (~70–80% JPEG-equivalent).
- **FR-002**: The sender MUST transmit the tiers inside the existing sealed E2EE envelope (as the
  video poster is already sent), so the recipient can render bubble/grid previews **before or without
  downloading the full image**.
- **FR-003**: Each tier MUST be persisted per message in local storage so no surface regenerates
  thumbnails on revisit.
- **FR-004**: The chat bubble MUST render from the **bubble** tier (not the full image); the all-media
  grid from the **grid** tier; the viewer's bottom strip from the **strip** tier; the viewer's main
  image from the **full** image.
- **FR-005**: Legacy messages without tiers MUST degrade gracefully (use the full image / legacy
  poster) until tiers exist for them (see FR-025 backfill).
- **FR-006**: Thumbnail generation and sending MUST happen in the background and MUST NOT block or
  delay the message send (consistent with existing media jobs).
- **FR-006a**: **Videos** MUST get **grid** and **strip** tiers by downscaling their existing poster
  image (no video re-encode); the video bubble keeps using the poster. So the grid and strip render
  right-sized thumbnails for both images and videos.
- **FR-006b**: A one-time, **bounded background backfill** MUST generate the tiers for media already
  on the device (throttled like existing media jobs, gated so it doesn't compete with interactive
  work); media not yet downloaded gets its tiers when fetched.

**Robustness (US2)**

- **FR-007**: The viewer MUST keep its current index valid when the item set changes (deletion,
  clear, empty album): clamp/reset the index, release stale per-item player references, and never
  render an out-of-range item.
- **FR-008**: The viewer and grids MUST show a clear placeholder for an item that is not downloaded or
  was cleared to free space — never a broken image.
- **FR-009**: The viewer MUST bound memory in large albums by releasing off-screen full-resolution
  images (only a small window of full images is held at once).
- **FR-010**: Zoom MUST reset per item so a zoom level never bleeds onto an adjacent item during fast
  swiping; the active item MUST always match what is shown.

**Fluidity / navigation (US3)**

- **FR-011**: The viewer MUST show a position indicator (current item and total).
- **FR-012**: The viewer MUST support keyboard navigation (move between items; close) with focus
  trapped while open and restored to the opener on close.
- **FR-013**: The bottom strip MUST keep the active item centered/visible as the user navigates.
- **FR-014**: Zoom and swipe MUST coexist with a clear way to exit zoom and resume swiping (an
  affordance), without accidental mode-locks.
- **FR-015**: Closing the viewer MUST return the user to the scroll position they opened it from (in
  the grid and in the chat).

**Cleanup (US4)**

- **FR-016**: Storage accounting (by type and by chat) MUST include thumbnail bytes, shown distinctly
  from the originals.
- **FR-017**: Deleting media MUST remove all of its thumbnail tiers (no orphaned thumbnails).
- **FR-018**: There MUST be a "free space but keep previews" action that removes full images while
  retaining the bubble/grid/strip tiers.
- **FR-019**: Cleanup MUST be reachable both app-wide (Storage management) and per-chat, with the
  per-chat all-media screen defaulting to that chat (plus an explicit app-wide option).
- **FR-020**: Adding the thumbnail fields MUST be a forward, data-preserving local storage migration.

**Accessibility / RTL / theme (US5)**

- **FR-021**: Images and controls in the viewer and grids MUST have meaningful accessible names (no
  empty alt), and the viewer MUST be operable without a pointer.
- **FR-022**: Album navigation MUST be correct in RTL (swipe direction and strip order), using
  direction-agnostic navigation rather than a physical horizontal-scroll offset.
- **FR-023**: The viewer MUST respect the app light/dark theme via existing theme tokens (not a
  hardcoded black background), with adequate contrast.

**Performance**

- **FR-024**: The all-media grid MUST generate/decode thumbnails gated on viewport visibility (not all
  at once) and cap concurrent decodes, so opening a large media library does not stall.

### Key Entities *(include if feature involves data)*

- **Image thumbnail set** — the three tiers (bubble / grid / strip) for a shared image, each a small
  encoded still; persisted per message in the local media store; carried in the sealed envelope.
- **Full image** — the original (compressed) image; loaded only for the viewer's main view; the
  largest reclaimable item in cleanup.
- **Media record** — extended to hold the tier blobs (plus the existing poster/original); the unit of
  storage accounting and deletion.
- **Album / viewer item** — an image/video entry the viewer paginates over; must always resolve to a
  valid in-range item with a renderable source or an explicit placeholder.
- **Storage usage breakdown** — per-type and per-chat totals that separate originals from thumbnails.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: With auto-download off, a recipient sees a bubble and grid preview for an incoming image
  **without** the full image being downloaded, in 100% of cases.
- **SC-002**: Scrolling a chat of 100+ images renders bubbles from thumbnails with no full-resolution
  image decoded per bubble (verified by no full-image fetch/decode on scroll).
- **SC-003**: Reopening the all-media grid shows previously generated thumbnails with no regeneration
  and no loading flash.
- **SC-004**: Deleting/clearing the viewed media never produces a broken image or an out-of-range
  error; the viewer shows a placeholder or closes — in 100% of tested cases.
- **SC-005**: Swiping a 200-image album keeps the number of full-resolution images held in memory
  bounded to a small fixed window.
- **SC-006**: The viewer shows a position indicator, is fully navigable by keyboard, and the strip
  tracks the active item.
- **SC-007**: Storage usage shows thumbnail bytes distinctly; deleting media leaves no orphaned
  thumbnails; "keep previews" frees the originals while previews still render.
- **SC-008**: In RTL, album navigation direction and strip order are correct; in light mode the viewer
  is not forced black; images/controls expose meaningful labels to assistive tech.
- **SC-009**: No image plaintext crosses the client/server boundary; the server relays only opaque
  ciphertext (now including the encrypted thumbnails).

## Zero-Knowledge Impact

This feature adds **encrypted thumbnails** to what's transmitted, so it crosses the client/server
boundary and is reviewed against Principle I.

- **What crosses the wire**: the three encrypted thumbnail tiers, generated on the sender and placed
  inside the **same sealed media envelope** that already carries the full image and the video poster.
  No new endpoint or frame type; the server sees a (slightly larger) opaque blob.
- **What the server sees**: unchanged in kind — opaque ciphertext + capability-style blob ids. It
  cannot read the image or its thumbnails, only relay/store the sealed bytes.
- **Encryption**: thumbnails are encrypted client-side with the same media-encryption path as the
  full image — no new key material, no plaintext at rest server-side.
- **Local-only state**: thumbnail blobs and the storage-usage breakdown live only in the device's
  local store; cleanup is local.
- **Metadata**: the only change is a modestly larger encrypted payload; no new user-identifying or
  content metadata is exposed. (Approximate byte sizes of the tiers are an unavoidable size signal,
  as for any media — unchanged in nature from today.)

## Assumptions

- Builds on the existing client media pipeline and `Media` store; server only relays the larger sealed
  envelope (no server/API/SQL change).
- Images get all three tiers; **videos** get grid + strip tiers by downscaling their existing poster
  (no video re-encode), and keep the poster for the bubble (FR-006a).
- Existing on-device media is **backfilled** with tiers via a bounded background pass (FR-006b).
- Default tier sizes per FR-001's starting point until clarified; JPEG (or the existing image encode
  format) for tiers.
- The full-screen viewer, the all-media grid, and the in-bubble album grid are the surfaces in scope.
- A local storage-version bump with a forward migration adds the tier fields without data loss.

## Dependencies

- Existing media pipeline: media-encode / media-meta / media-jobs / media-transfer and the `Media`
  store; the sealed media envelope (the same path the video poster uses).
- Spec 1011/1012/1013 chat-detail + media rendering surfaces (chat bubble, album grid, viewer).
- Storage-management settings surface (global) and the per-chat all-media screen.

## Out of Scope

- Server-side thumbnailing or any server visibility into media (forbidden by Principle I).
- Video **re-encoding** (videos get grid/strip by downscaling the existing poster, not re-encoding;
  no new full-video processing or video bubble tier beyond the poster).
- Changes to image compression tiers for the **full** image (sd/hd/original) beyond what the tiers add.
